# GPU presentation

Gameplay, scene JSON, authoritative transforms, collision and interpolation
policy are unchanged. Ordinary interpolated browser frames now blend, compose,
validate and cull displayed poses on the GPU
([decision 014](../adr-014-gpu-presentation-and-culling.md)); the CPU pass remains
the exact reference and opt-out.

`PresentedTransforms` is no longer rewritten by those frames. After one,
`PresentationState::gpu_pending()` is true and the store holds the previous
CPU-prepared values. Code that reads presented poses outside development
inspection chooses one of:

```rust
// Materialize the last GPU-presented frame's exact CPU reference on demand.
// Returns false once a tick, refresh or reset changed that frame's inputs.
if engine.presentation().gpu_pending() {
    engine.prepare_presented_transforms();
}
let pose = engine.app.world().resource::<PresentedTransforms>().get(entity);
```

or keeps CPU presentation for every frame with
`BrowserApp::set_gpu_presentation(false)`. Authoritative reads through
`GlobalTransforms` are unaffected; prefer them for gameplay decisions.

Custom consumers of borrowed `RenderFrame` values check `frame.gpu()`. A GPU
frame's `visible_indices()` lists every candidate slot, including invalid ones
the GPU hides; `slot_nodes()` maps slots to input nodes, and `culling()` and
`instance_budget()` describe the GPU's work. `model()` and `pose_rows()` are not
prepared for GPU frames. `Engine::extract_frame` is unchanged and remains the
CPU path; `Engine::extract_gpu_frame(aspect, alpha)` prepares a GPU frame.

For GPU frames, `RenderStats::gpu_visible` and the browser's `visible_instances`
are read back from a completed frame a few frames old, and `instances` is that
count within the instance budget. Candidate, invalid and missing-asset counts are
current. Compare visibility across frames rather than expecting a same-frame
count.

Custom consumers of `GpuPresentation`: `NodeLocals` (80 bytes) became separate
`current` and `previous` `NodePose` streams (40 bytes each). `current` covers every
node (it borrows the hierarchy's cached locals) but is stamped only for active
nodes when they change. When `shift` is set and you applied the gather just
before this one, copy every current pose into its previous slot before applying
stamped records; after a missed copy, stop blending until a later shift you
apply. `stamped` gives each stream's stamped-record count for skipping clean
streams one gather behind.

With GPU presentation, `BrowserApp` now pipelines fixed ticks
([decision 015](../adr-015-pipelined-fixed-ticks.md)). `Presentation` systems can
run between a tick's stages and observe its gameplay effects and fixed time
before its propagated transforms; call `set_tick_pipelining(false)` if frame-rate
gameplay needs a consistent view, or `Engine::complete_pending_tick` before an
out-of-band read. A tick completed that way stays hidden from GPU frames until it
is due; `Engine::reveal_ticks_ahead` presents it earlier.

When a tick completes ahead, `Engine::run_ahead` also gathers its GPU inputs, and
frames before it is due present them with `GpuPresentation::hold` set. Custom
consumers must then keep presenting the inputs they applied last, at `alpha`, and
apply the held gather at the first view without `hold` (or immediately if they
applied nothing in this `identity` yet).

Hosts that drive `Engine` and `Renderer` themselves can copy the pipeline's
upload staging: after `run_ahead` completes a tick (`tick_completed_ahead()`),
pass `Engine::gpu_current()`'s poses and version to
`Renderer::prestage_gpu_current`. A GPU frame whose gather has the same
`GpuPresentation::current_version` then copies them on the GPU. After
`render_frame` returns `RenderStats::submitted == false` (a suspended, occluded or
recovering surface), complete and reveal any pending tick before the next GPU
frame, as `BrowserApp` does, because current poses are borrowed from the
hierarchy.

Agents: `present` and `capture` accept `"gpu": true` together with an alpha to
preview the GPU path; without it they keep the exact CPU path. Observations and
`PresentationState` inspection include `gpu_pending`, and inspecting
`PresentedTransform` materializes a pending GPU frame first. Stress Lab accepts
`?presentation=cpu` for same-build comparisons; recordings and profiles report
the selected path. Profiles add `presentation_compute` GPU samples and the
counters listed in [profiling](../profiling.md).
